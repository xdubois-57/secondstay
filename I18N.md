# I18N.md

# Internationalisation — FR / EN / NL / DE

## 1. Exigence

Le support multilingue est une **capacité de base dès l’itération 0**.

Langues obligatoires :

| Code | Langue |
|---|---|
| `fr` | Français |
| `en` | English |
| `nl` | Nederlands |
| `de` | Deutsch |

Le français est la langue par défaut initiale, mais l’architecture ne doit jamais supposer une seule langue.

## 2. Deux catégories de textes

### Textes système

Exemples :

- boutons ;
- erreurs ;
- navigation ;
- statuts ;
- labels formulaires ;
- messages sécurité ;
- confirmations ;
- chaînes PWA.

Ils vivent dans des catalogues de traduction versionnés avec le code.

### Contenus éditoriaux

Exemples :

- page d’accueil ;
- description du logement ;
- activités ;
- consignes ;
- déchets ;
- textes saisonniers ;
- e-mails administrables ;
- certains contenus juridiques.

Ils vivent en DB et sont traduisibles.

## 3. Clés de traduction

Préférer des clés stables par domaine :

```text
auth.login.title
booking.status.confirmed
booking.price.total
stay.wifi.title
inspection.checkout.photo_required
admin.settings.smtp.test
```

Ne pas utiliser le texte français comme clé.

## 4. Organisation des catalogues

Exemple :

```text
translations/
├── fr/
│   ├── common.php
│   ├── auth.php
│   ├── booking.php
│   └── stay.php
├── en/
├── nl/
└── de/
```

Un format JSON/YAML/PHP est possible si cohérent, testable et sûr.

## 5. Fallback

Ordre proposé :

1. préférence utilisateur enregistrée ;
2. langue sélectionnée explicitement ;
3. `Accept-Language` si supporté ;
4. langue par défaut du site ;
5. `fr` ultime.

Pour un contenu DB absent dans la langue demandée :

- utiliser le fallback configuré ;
- ne jamais afficher une clé brute ;
- l’admin doit voir quels contenus restent non traduits.

## 6. Sélecteur de langue

Accessible :

- public ;
- pages auth ;
- espace client ;
- séjour ;
- administration.

La préférence persiste via compte et/ou cookie strictement fonctionnel.

## 7. Formatage localisé

Utiliser les APIs/locales appropriées pour :

- dates ;
- heures ;
- montants ;
- nombres ;
- durées.

Le stockage métier reste canonique :

- dates ISO ;
- timestamps UTC ou timezone explicitement définie ;
- montants en unités entières/money value ;
- devise EUR.

Ne jamais parser une valeur financière critique à partir d’un texte localisé sans validation stricte.

## 8. E-mails et push

La langue du destinataire détermine le template.

Chaque notification doit avoir ses versions FR/EN/NL/DE ou un fallback explicite.

Les sujets sont traduits eux aussi.

## 9. Contrats et textes juridiques

Les documents juridiques sont versionnés par :

- document/type ;
- version ;
- locale ;
- date d’effet.

Une réservation conserve :

- la version ;
- la locale ;
- le contenu/snapshot accepté lorsque requis.

Un changement de traduction juridique ne doit pas réécrire l’historique.

## 10. Contenus administrables

L’admin voit clairement l’état de traduction :

```text
FR ✓
EN ✓
NL !
DE ✓
```

Il peut :

- éditer chaque langue ;
- copier le texte source comme point de départ ;
- éventuellement demander une traduction LLM ;
- prévisualiser ;
- publier.

Une traduction LLM n’est jamais publiée silencieusement pour un texte juridique.

## 11. SEO multilingue

Chaque langue peut avoir :

- title ;
- meta description ;
- Open Graph ;
- contenu structuré.

Prévoir URLs/locales cohérentes, par exemple :

```text
/fr/...
/en/...
/nl/...
/de/...
```

ou autre stratégie explicite stable.

Ajouter `hreflang` si l’architecture URL retenue le permet.

## 12. PWA

Le manifest et les métadonnées visibles doivent être cohérents avec la locale.

Le contenu offline respecte la langue choisie.

Éviter de mélanger des fragments de plusieurs langues dans le cache visible.

## 13. IMAP / documents

Les mails reçus gardent leur langue originale.

Ne pas traduire automatiquement le corps original dans l’archive.

Une traduction d’assistance, si ajoutée plus tard, doit rester clairement distincte de l’original.

## 14. Activités locales et LLM

Les activités générées peuvent être produites pour les quatre langues ou traduites après structuration.

Toujours conserver les données factuelles structurées indépendamment du texte traduit :

- date ;
- lieu ;
- source ;
- URL ;
- besoin réservation ;
- dernière vérification.

## 15. Tests

### Unitaires

- résolution locale ;
- fallback ;
- catalogues complets ;
- placeholders identiques entre langues ;
- formatage date/money ;
- absence de clé manquante dans parcours critiques.

### E2E

Au minimum, chaque release doit exécuter les parcours critiques dans les quatre langues ou via une matrice couvrant explicitement FR/EN/NL/DE.

Critiques :

- home ;
- signup/login ;
- réservation ;
- paiement fake ;
- documents/contrat ;
- Mon séjour ;
- état des lieux ;
- erreurs principales.

### Régression

Une nouvelle clé en FR sans équivalent EN/NL/DE doit faire échouer le check de traduction, sauf exception explicitement marquée et temporaire.

## 16. Definition of Done i18n

Une fonctionnalité utilisateur n’est pas terminée si :

- ses textes système ne sont pas traduits FR/EN/NL/DE ;
- son contenu éditorial n’est pas traduisible ;
- ses notifications ne respectent pas la locale ;
- son document contractuel ignore la locale ;
- ses tests ne couvrent pas le fallback et au moins les parcours multilingues requis.

## 17. Itération 3 — comptes et e-mails

### 17.1 Nouveaux catalogues

| Domaine | Contenu |
|---|---|
| `account` | inscription, confirmation, réinitialisation, profil, appareils, clés d’accès, RGPD |
| `mail` | sujets et corps des e-mails transactionnels |
| `webauthn` | messages d’erreur des clés d’accès |

### 17.2 Langue des e-mails

Un e-mail est rendu dans la **langue du destinataire**, pas dans celle de la
requête qui l’a déclenché : `MailService::send()` bascule le traducteur sur la
locale du compte le temps du rendu, puis la restaure. Le sujet provient de
`mail.<template>.subject` et l’en-tête `Content-Language` porte la locale.

Les liens contenus dans un e-mail portent le préfixe de langue du
destinataire (`/nl/account/confirm?token=…`).

### 17.3 Préférence de langue du compte

La langue préférée est stockée sur le compte (`user.locale`) et prime sur le
cookie et sur `Accept-Language` dès qu’une session est ouverte. La modifier
depuis l’espace client redirige immédiatement vers la même page dans la
nouvelle langue.

### 17.4 Erreurs techniques

Les erreurs SMTP et WebAuthn ne sont jamais exposées telles quelles : le
serveur renvoie une **clé de traduction** (`mail.error.*`, `webauthn.error.*`)
que l’interface traduit. Un message d’erreur du navigateur ou du serveur de
messagerie n’apparaît donc jamais en anglais dans une page française.

## 18. Itération 4 — notifications et application installable

### 18.1 Nouveaux catalogues

| Domaine | Contenu |
|---|---|
| `notification` | sujet d'e-mail, titre et texte poussés, libellé d'action, préférences |
| `push` | erreurs du push navigateur |
| `pwa` | manifeste, raccourcis, page hors ligne |

### 18.2 Un événement = un jeu de clés

Chaque événement notifiable expose les mêmes clés : `subject`, `title`,
`body`, `mail_body`, `action`. Le titre et le texte poussés sont volontairement
plus courts que le corps de l'e-mail. Ajouter un événement ne demande donc
aucun gabarit supplémentaire, seulement quatre traductions.

### 18.3 Langue de la notification

Comme pour les e-mails, la notification poussée est rendue dans la langue du
**compte destinataire**, pas dans celle de la requête qui l'a déclenchée. La
charge utile transporte sa locale, et le service worker la restitue au
navigateur (`lang` de la notification).

### 18.4 Manifeste localisé

Le manifeste est servi par langue (`/manifest.webmanifest?locale=nl`) : nom,
description, `start_url` et raccourcis suivent la langue de la page qui le
déclare. Chaque page publie le manifeste correspondant à sa propre langue.

### 18.5 Hors ligne

Une page hors ligne existe dans chacune des quatre langues et est préchargée
par le service worker. Le cache de pages est lui aussi nommé par langue : un
visiteur néerlandophone ne se voit jamais servir une page française en
secours.

## 19. Itération 5 — dates et montants

### 19.1 Catalogue

Le domaine `booking` couvre les règles de séjour, le calendrier, le devis et
les tarifs. Il ne contient **ni symbole monétaire ni format de date** : ces
deux aspects relèvent du `Formatter`, donc d'ICU.

### 19.2 Séparation formatage / calcul

La logique financière est canonique : des entiers de centimes, identiques dans
les quatre langues. Seul l'affichage change — séparateur de milliers,
position du symbole, décimales. Les tests vérifient que les quatre rendus
portent exactement les mêmes chiffres tout en restant distincts.

### 19.3 Calendrier

Le nom du mois et les abréviations des sept jours proviennent d'ICU
(`monthname`, `weekday_names()`), jamais d'une table écrite à la main. La
semaine commence le lundi, convention des quatre pays visés.

### 19.4 Côté navigateur

Le navigateur ne calcule aucun prix : il reçoit des entiers de centimes et les
formate avec `Intl.NumberFormat`, dans la locale de la page. Les dates sont
formatées avec `Intl.DateTimeFormat` en UTC, afin qu'une date choisie près de
minuit ne glisse jamais d'un jour.

## 20. Itération 6 — réservation

Le domaine `booking` s'étend aux états, sous-états, événements de timeline,
codes promotionnels et parcours. Chaque état et chaque type d'événement porte
sa propre clé : l'interface n'affiche jamais une valeur technique.

Les e-mails de réservation et l'alerte de liste d'attente partent dans la
langue du compte ou de l'inscription, pas dans celle de la requête qui a
déclenché l'envoi. La langue choisie au moment de la réservation est stockée
avec le séjour, de sorte que les documents produits plus tard restent
cohérents.

## 21. Itération 7 — paiements

Le domaine `payment` couvre les composants financiers (acompte, solde,
caution, ménage, taxe de séjour, ajustement, remboursement), les états, le
cycle de la caution, l'échéancier, les instructions de virement et le suivi en
administration. Chaque valeur d'énumération porte sa propre clé — `payment.kind.*`,
`payment.status.*`, `payment.hold.*` — obtenue par `labelKey()` : l'interface
n'affiche jamais une valeur technique.

Les erreurs de paiement remontent des services sous forme de clés
(`payment.error.*`), jamais de messages en dur : le même code sert les quatre
langues, et un message de fournisseur en anglais n'atteint jamais la page.

Trois points méritent l'attention :

- **la référence de virement** insérée dans le QR code EPC contient le libellé
  du composant traduit dans la langue du séjour, afin que le voyageur
  reconnaisse ce qu'il paie dans son relevé bancaire ;
- **le montant** du message EPC suit strictement le format de la
  spécification — point décimal, deux décimales — indépendamment de la locale
  d'affichage : c'est une donnée machine lue par une banque, pas un texte ;
- **les nouveaux événements de séjour** (`booking.event.payment_*`) sont
  traduits dans les quatre langues, la timeline étant lue par le client comme
  par le propriétaire.

Les libellés des réglages `payment.*` et `tax.*` existent en FR/EN/NL/DE, y
compris les messages d'erreur de validation de l'IBAN, du BIC et de la devise.

## 22. Itération 8 — contrats et courrier

Le contrat existe en FR/EN/NL/DE **dans son intégralité** : titres, libellés,
clauses et mentions viennent tous du domaine `contract`, aucune phrase n'est
écrite en dur dans le générateur. La langue retenue est celle du séjour, pas
celle de la requête qui déclenche la génération : un administrateur qui
consulte en français produit malgré tout le contrat néerlandais d'un séjour
néerlandais.

L'acceptation conserve la langue lue. Un séjour accepté en allemand garde la
trace « version 1, langue DE » même si le modèle est ensuite traduit
autrement : c'est la condition pour savoir, plus tard, ce que le client a
réellement accepté.

Deux points techniques valent d'être notés :

- **le codage du PDF.** Les polices standard du format utilisent
  `WinAnsiEncoding`, qui couvre l'intégralité des lettres des quatre langues,
  l'euro, les guillemets français et l'apostrophe typographique. Les rares
  caractères hors table sont translittérés plutôt que rendus par un carré
  vide ;
- **les messages reçus.** Les en-têtes encodés (RFC 2047) et les corps dans
  un jeu de caractères autre qu'UTF-8 sont convertis à la réception. Un jeu de
  caractères inconnu ou menteur ne fait jamais perdre le message : la lecture
  retombe sur Latin-1, qui n'échoue jamais.

Les nouveaux domaines `document` et `mailbox` couvrent les natures de
document, les provenances, les règles de rattachement et les erreurs de la
boîte de réception, dans les quatre langues.

## 23. Itération 9 — exploitation et calendriers

Les domaines `operations` et `calendar` couvrent les phases de checklist, les
libellés de chaque ligne, les entrées du tableau « À faire », les portées de
calendrier et les erreurs, dans les quatre langues.

Un flux ICS est rendu dans la **langue de son destinataire**, pas dans celle de
la requête qui l'a déclenché : le flux d'un séjour néerlandais est en
néerlandais, celui d'un responsable dans la langue de son compte, et celui de
l'administration dans la langue de l'installation. C'est la même règle que
pour les e-mails et les contrats.

Le nom du calendrier lui-même est traduit — `X-WR-CALNAME` — de sorte qu'un
agenda affiche « Mes séjours » ou « Meine Aufenthalte » selon l'abonné, et non
une chaîne technique.

## 24. Itération 10 — mon séjour

Le livret d'accueil n'est pas traduit à la volée : il existe **réellement**
en quatre langues, une ligne par bloc et par langue. L'administration montre,
pour chaque bloc, dans quelles langues il est renseigné — un livret utile en
français mais vide en allemand doit se voir avant qu'un voyageur allemand ne
le découvre.

Lorsqu'une traduction manque, le bloc de la langue par défaut prend le relais
plutôt que de disparaître : trouver l'information dans une autre langue vaut
mieux que ne pas la trouver du tout. C'est le seul endroit du produit où ce
repli s'applique à du contenu saisi, et il est délibéré — un voyageur devant
une porte close a besoin du code, pas d'une page vide.

Ce repli comble une **lacune** — bloc jamais traduit, ou traduit puis vidé — et
ne défait jamais une **décision**. Un bloc renseigné que le propriétaire a
retiré du web ouvert, ou dépublié du livret, n'est pas remplacé par une autre
langue : cette adresse-là répond 404. Sans cette limite, la publication langue
par langue ne voudrait rien dire.

Un lien invité conserve la langue choisie à sa création : le voyageur le
transmet à des personnes qui ne parlent pas nécessairement la sienne, et le
lien doit s'ouvrir dans la langue qu'il a choisie pour elles.

La carte et la source d'un bloc (§55) suivent la même règle que le texte :
elles vivent **par bloc et par langue**, et ne sont jamais dérivées d'une autre.
Une commune néerlandophone et une commune francophone ne publient pas la même
page de collecte, et un lien vers la mauvaise est pire qu'aucun lien. Le libellé
du lien est saisi dans la langue du bloc ; la date de vérification est rendue au
format de la langue affichée.

Le domaine `stay` couvre les phases, les blocs, les codes d'accès, le décompte
avant l'arrivée, les liens invité, la carte et la source, dans les quatre
langues.

## 25. Itération 11 — états des lieux et incidents

Deux domaines nouveaux, complets dans les quatre langues : `inspection` et
`incident`.

Le point délicat est le **nom des zones**. Une zone porte deux choses
distinctes :

- un **code** technique (`kitchen`), stable, indépendant de la langue, qui
  sert d'identifiant et de clé de traduction ;
- un **nom** saisi par le propriétaire, une ligne par langue, dans
  `inspection_zone_translation`.

Une zone sans nom saisi retombe sur `inspection.zone.<code>`, fourni en
FR/EN/NL/DE : une installation neuve est donc immédiatement utilisable dans
les quatre langues, et le propriétaire ne personnalise que ce qu'il veut. Le
tableau de complétude de l'administration montre les noms **personnalisés**,
et dit explicitement que l'absence de nom n'est pas une absence de traduction.

Une zone créée par le propriétaire, elle, n'a pas de libellé intégré : son nom
doit être saisi langue par langue, et le tableau de complétude le signale.

L'état des lieux est enregistré avec la langue dans laquelle il a été rempli,
comme le contrat : c'est celle du voyageur au moment du constat, et elle sert
de repli à l'affichage ultérieur.

Les messages de refus sont des clés, jamais des phrases construites : un
départ bloqué faute de photo affiche `inspection.error.photos_required` dans
la langue de la page, suivi des zones concernées, nommées elles aussi dans
cette langue.

## 26. Itération 12 — conformité et textes légaux

Quatre domaines nouveaux, complets dans les quatre langues : `compliance`,
`legal`, `tax`, `police` et `privacy`.

Le domaine `compliance` est le plus dense : chacun des dix-huit sujets porte
cinq textes — libellé, définition, applicabilité, où trouver, impact — soit
trois cent soixante entrées. C'est volontaire : un assistant qui n'expliquerait
qu'en français ne servirait pas un propriétaire néerlandophone, et un sujet à
demi traduit vaut moins qu'un sujet absent, parce qu'il donne l'illusion d'être
couvert.

Les **textes légaux** ne sont pas des traductions au sens habituel : ce ne sont
pas des clés, mais des contenus éditoriaux, versionnés langue par langue. Deux
conséquences :

- une version est publiée **pour toutes les langues à la fois**. Une « version
  3 » qui n'existerait qu'en français ferait accepter à un voyageur
  néerlandais une version fantôme. Quand une langue n'a pas de texte, la
  publication le dit explicitement plutôt que de l'inventer ;
- l'acceptation enregistre la **langue effectivement lue**, celle de la page où
  la case a été cochée. C'est cette version-là, dans cette langue-là, qui sera
  opposable.

Le repli reste possible à l'affichage — mieux vaut un texte lisible dans une
autre langue qu'aucun texte — mais l'acceptation enregistre alors la langue
réellement servie, jamais celle qui était demandée.

Les **montants et dates** de la taxe de séjour suivent les règles de l'§7 :
stockage en centimes et en `Y-m-d`, formatage à l'affichage selon la langue.

## 27. Itération 13 — contenu local généré

Le domaine `local` couvre l'écran d'administration, les catégories d'activité,
les groupes d'affichage et les messages du pipeline, en FR/EN/NL/DE.

Deux points particuliers.

**La langue de rédaction est une consigne, pas un post-traitement.** Le prompt
système demande explicitement de rédiger titres et résumés dans la langue du
séjour, et les activités sont stockées **par langue** : le couple (séjour,
langue) a son propre jeu. Traduire après coup un contenu produit en français
donnerait un texte de seconde main, et coûterait un appel de plus.

Conséquence assumée : une langue pour laquelle rien n'a été produit n'affiche
simplement pas de suggestions. La page « Mon séjour » reste utilisable — mieux
vaut une section absente qu'une section dans la mauvaise langue.

**La consigne proposée par le bouton « Générer le prompt » est elle-même une
clé de traduction** (`local.suggested_prompt`), paramétrée par la localisation
et le nom du logement. Un propriétaire néerlandophone reçoit donc une
proposition en néerlandais, qu'il reste libre de réécrire entièrement.

## 28. Itération 14 — clôture de l'exploitation

Quatre domaines nouveaux, complets en FR/EN/NL/DE dès la livraison :

| Domaine | Couvre |
|---|---|
| `calendar.import` | flux externes : plateformes, états, erreurs, actions |
| `dispute` | natures, états, actions, événements, pièces au dossier, refus |
| `report` | indicateurs, champs, onglets du classeur, avertissement |
| `quota` | catégories mesurées, unité, refus d'écriture |

Trois points particuliers.

**Le classeur exporté est traduit dans la langue de la page qui l'a demandé.**
Noms d'onglets, en-têtes de colonnes et libellés d'indicateurs passent par le
catalogue avec la locale de la requête, pas par une locale par défaut. Un
propriétaire germanophone télécharge donc un classeur allemand — et le test le
vérifie en relisant les onglets `Übersicht` et `Aufenthalte`.

**L'avertissement du reporting est une traduction, pas un ornement.** Il dit
que ces chiffres ne sont ni un conseil fiscal ni une déclaration ; il figure à
l'écran et dans le classeur, dans les quatre langues. Une mise en garde qui ne
serait affichée qu'en français ne protégerait personne.

**Les états techniques ne fabriquent pas de clés.** Une synchronisation
échouée sur un code HTTP est journalisée avec son code (`http_503`), mais
l'écran n'affiche que l'un des quatre libellés traduits. Dériver une clé de
traduction d'un code renvoyé par un tiers produirait, tôt ou tard, un libellé
manquant dans les quatre langues à la fois.

## 29. Consolidation — planificateur, QR physiques et garde-fou de clés

Deux domaines nouveaux, complets en FR/EN/NL/DE dès la livraison :

| Domaine | Couvre |
|---|---|
| `scheduler` | tâches périodiques : libellés, états, résultats, actions, ligne cron |
| `stay.info` | pages ouvertes depuis un QR : repli de langue, mention de page |

Trois points particuliers.

**Un résultat de tâche est une clé et un nombre, jamais une phrase
assemblée.** `scheduler.detail.mail_imported` reçoit `{count}` ; l'écran
d'exploitation compose la phrase dans sa langue. La tentative naturelle —
stocker « 3 messages importés » au moment de l'exécution — figerait la langue
du cron, qui n'en a aucune, et rendrait l'historique illisible pour un
propriétaire qui change de langue.

**Un message de fournisseur n'est jamais affiché.** Une boîte injoignable, un
flux muet ou une exception donnent une clé traduite ; le message d'origine part
au journal. C'est autant une règle de langue qu'une règle de sécurité : ces
messages sont écrits en anglais par un tiers et peuvent porter un hôte ou un
chemin.

**Une page ouverte depuis un QR tombe sur la langue du logement quand le bloc
n'existe pas encore dans celle du visiteur**, et le dit — `stay.info.fallback`.
C'est le seul endroit du produit où le repli est **annoncé** plutôt que
silencieux : le visiteur est debout devant un appareil qu'il ne sait pas faire
marcher, et une information dans une langue qu'il ne lit pas doit s'expliquer
elle-même. Ailleurs, une section absente reste préférable à une section dans
la mauvaise langue.

### Le garde-fou qui manquait

La parité entre catalogues ne détecte pas une clé **inventée** : elle manque
dans les quatre langues à la fois, donc symétriquement. Elle ne casse rien de
visible non plus, puisque le traducteur rend le dernier segment lisible.

C'est exactement ce qui se passait sur l'onglet « toutes » de la liste des
réservations : `booking.admin.all` n'existait nulle part, et le mot « All »
s'affichait en français, en néerlandais et en allemand.

Le contrôle statique vérifie désormais que toute clé écrite littéralement dans
`src/` ou `templates/` existe. Les préfixes de concaténation — `t('stay.block.'
~ code)` — sont écartés à leur terminaison, un point ou un tiret bas : un
contrôle qui ne signalerait que des faux positifs finirait par être ignoré.

**Le texte alternatif d'une illustration est traduit, et son repli est
explicite.** Une photo de local à poubelles s'adresse précisément à quelqu'un
qui cherche : l'alternative textuelle suit la langue de lecture, retombe sur la
légende traduite du média, puis sur le titre du bloc. Elle n'est jamais vide.

## 30. Repli ASCII déterministe

Trois endroits ramènent du texte à l'ASCII : les initiales de l'icône
installée, les slugs et les caractères hors `WinAnsiEncoding` du PDF. Les
quatre langues du produit y amènent des lettres accentuées, deux ligatures
(`œ` en français, `ĳ` en néerlandais), l'eszett allemand et les guillemets
français.

Ce repli ne dépend plus de l'hôte. `Support\Ascii` porte une table écrite dans
le dépôt, là où `iconv('UTF-8', 'ASCII//TRANSLIT', …)` rendait « Été » par
« Ete » sur glibc et par « 'Et'e » sur la libiconv de macOS et des BSD. Une
installation allemande et une installation française produisent donc les mêmes
slugs, et l'icône affiche les mêmes initiales, quel que soit l'hébergement.

`ß` devient `ss` et non `s`, `œ` devient `oe`, `ĳ` devient `ij` : la règle
suivie est celle de la langue d'origine, pas la simple suppression du
diacritique. Ce que la table ne connaît pas est retiré ; aucune apostrophe ni
aucun guillemet n'est introduit là où la source n'en portait pas.

Conséquence assumée : un titre écrit intégralement dans une écriture non
latine ne produit plus de slug translittéré mais un slug vide, que le
formulaire refuse par `content.error.slug_required`. Le produit est spécialisé
pour la France et ses quatre langues (AGENTS.md §1.3) ; mieux vaut une erreur
lisible qu'un identifiant d'URL dont la forme dépendrait de la présence de
`intl` sur l'hébergement.

## 31. L'installeur autonome est en français seul

`bootstrap/bootstrap.php` (ARCHITECTURE.md §28.3) n'affiche que du français, et
c'est une décision, pas un oubli.

**Il ne peut pas faire autrement au moment où il parle.** Il s'exécute avant que
le moindre fichier du projet n'existe sur le disque : pas de
`translations/`, pas de `Translator`, pas de `vendor/autoload.php`. Embarquer
quatre catalogues dans le fichier lui-même en ferait une cinquième copie des
mêmes chaînes, à maintenir à la main, sans le contrôle de complétude que
`## 15. Tests` applique aux vrais catalogues — et ce contrôle est précisément ce
qui empêche une traduction de rester en retard sans que personne ne le voie.

**Son public n'est pas celui du produit.** Le site s'adresse à des voyageurs de
quatre langues ; l'installeur s'adresse une seule fois à la personne qui
possède l'hébergement, et rien de ce qu'il affiche n'est jamais revu ensuite.
Il se supprime après usage.

Tout ce qu'il installe, en revanche, est multilingue dès la première requête :
l'assistant d'installation vers lequel il redirige suit l'`Accept-Language` du
navigateur comme n'importe quelle autre page (§5).
